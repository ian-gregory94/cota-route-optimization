What a fair test of Experiment 1 actually shows

Route-level passenger assignment believes its plans cut unserved demand 22.7% at slightly negative cost. Scored honestly, those same plans deliver 7.2% — at +2.5% cost. Every one of them is beaten outright by a plan the corrected model finds. That is Experiment 1's error, reproduced under control with demand, solver and search budget all held fixed.

Getting there required retracting the first correction too. The ablation that produced it searched 20× less hard than Experiment 1 did, in the direction that flattered its own conclusion.

First: was the earlier comparison fair?

No. It compared a weak search against a strong one, and the weakness pointed its way.

Experiment 1 was solved with 400,000 iterations, 20 restarts and full candidate width. The ablation that "corrected" it ran 20,000 iterations, no restarts, width 24 — a 20× gap. Any difference across that gap conflates the model change with the search budget. The mechanism of the original error

Route-level assignment overstates its own coverage gain by about 3× and reports a cost reduction where there is a 2.5% increase. It cannot see either, because it never asks where a displaced traveller actually goes. The path-based models report exactly what they deliver, because the yardstick is their own machinery.

And the plans are genuinely worse, not merely mis-reported: all seven route-level plans are strictly dominated by some path-based plan — beaten on cost and coverage at once.

Does crowding bind? No.

Measured at the peak load point from assigned link volumes, not route averages.

Experiment 1 applied crowding to a route's average passengers per trip, which never triggers. With path assignment the real answer is computable: each assigned trip rides a known span of a known pattern, so segment volumes accumulate and the maximum is the peak load point.

Two bugs the verification caught

Both were silently flattering every path-based number.

The path-set approach caches candidate journeys and re-prices them as headways change. A cached set is a subset of what the router can find, so its cost must always be greater than or equal to a fresh RAPTOR run. The first verification pass showed the cache coming out cheaper — impossible, and therefore a bug.

Bug 1 · truncated journeys

Journey reconstruction walked parent pointers backward from the destination and returned whatever it had if the trace ran out. The legs it dropped are the ones nearest the origin, so those paths priced far below their true cost. It now returns nothing unless the back-walk actually reaches a source stop.

Bug 2 · route headway vs pattern headway

A ride leg was priced at its route's headway. But a route running several pattern variants is proportionally less frequent on each one, and a passenger riding a specific variant only benefits from that variant's trips. The router had this right; the evaluator did not — a constant 7.5-minute understatement on every one-transfer journey. Legs now carry a structural pattern-to-route frequency multiplier.

A third, smaller error surfaced with them: because labels carry between RAPTOR rounds, a traveller's first boarding could happen in round two and get charged a transfer penalty. Labels now track boarding count rather than round number.

Enumeration now rejects any candidate path that does not re-price to the cost the router reported for it. That check moved rejections from 64,382 to 235 and cut the cached set's cost error from −11.07% to −0.17%.

Verification

What was checked, and what the checks say.

Does the cached path set miss better journeys?

The optimizer chooses among candidate journeys enumerated at baseline headways plus five scenarios. Full RAPTOR was re-run under the actual optimized headways and compared per OD pair. The answer depends on how far the plan moves from today's schedule, and that dependence is itself a limitation worth stating.

Near today's schedule the cache is essentially exact. For the aggressive cost-weighted plans it is not: a sixth of demand has a better journey the optimizer could not see. Those plans' costs are therefore conservative — the true cost is lower than reported — but the optimizer was choosing against a slightly wrong objective in that region, so the λ = 0.25 end of the frontier is the least trustworthy part of it. The fix is to re-enumerate paths under the optimized plan and re-solve until the set stops changing.

Does the resource envelope actually hold?

Verified

The model's baseline vehicle-hours reproduce the GTFS schedule exactly — relative error 0.0 — because baseline headways are defined as k·T/n_trips. Every reported plan sits under 2,517.2 revenue vehicle-hours and under every per-period peak-vehicle cap. Every headway lies on its allowed ladder; no route-period loses service.

Experiment 1's plans were additionally re-evaluated by a second scalar implementation sharing no code with the vectorized solver. Maximum relative disagreement: 6.5 × 10⁻¹⁶.

Is the fleet constraint the right one?

NTD reports COTA operating 198 vehicles in maximum service. The schedule sweep finds 171 simultaneously-running trips and the model's continuous approximation 176.5. The real requirement is 12% above what the model constrains to, so the peak-fleet cap is conservative — the optimizer had less headroom than COTA actually has. That is the safe direction for a claim about staying inside current resources.

What is still missing

Separating what more compute fixes from what it cannot.

Fixable by iterating

  1. Re-enumerate paths against the optimized plan and re-solve until the set stops changing. This is now the largest known source of error: 17.6% of demand has a better journey missing from the cache under the aggressive plans. A fixed-point loop closes it, and the infrastructure to run it cheaply now exists.
  2. Hyperpath assignment. A traveller is assigned to the single best pattern, not the combined frequency of every pattern that would serve them. 52 of 78 route-directions run one pattern and the dominant pattern carries 86% of trips, so the error is small — but it understates effective frequency everywhere.
  3. Vehicle blocks from GTFS block_id. Present and unexploited. Gives a true peak-vehicle count including interlining, closing the 171-vs-198 gap against NTD.

Not fixable by compute

  1. Stop- and trip-level APC boardings. Still the binding constraint on everything. Demand here is LODES commute flow; non-work travel is simply absent, which matters most at midday. Only 24.7% of Central Ohio commute flow has a stop within walking range at both ends, and the model covers the top 65% of that.
  2. Period demand shares. LODES has no time dimension, so how demand splits across the six service periods is assumed. It directly scales how much each period's decisions matter.
  3. Observed runtime distributions. GTFS-Realtime feeds are public and the collector is built and tested, but nothing has been collected. Until then the reliability term stays a zero-weighted placeholder.
Infrastructure, so this stays affordable

Setup is cached content-addressed on its inputs — 128 MB covering the baseline, router, zones, OD table and path sets — taking build time from 11 minutes to 0.2 seconds. Evaluation is 5× faster after fixing a cache key that spanned all 173 route-periods, so a single headway change invalidated all six periods. Every solved cell is checkpointed, so a multi-hour run resumes rather than restarts.

That matters for correctness, not just convenience: the reason the first correction was wrong is that running it properly was too slow to be tempting.

Standing caveat

None of this is a COTA recommendation. It is a model of COTA built from public data, calibrated where public data allows, and honest about the rest. It has now retracted its own answer twice — once for a modelling error, once for an impatient search — which is the part worth trusting.
